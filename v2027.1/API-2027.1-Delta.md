# Advance Design API — 2027.1 Delta

*Advance Design · OpenAPI schema · Comparative analysis*

This document compares the OpenAPI schema shipped with **Advance Design 2027** with the one shipped with **Advance Design 2027.1**. It covers the whole public contract: element editing and deletion, Expert design, automatic combinations and model settings, user-defined cross-sections, structural systems and edge releases, reference geometry, generalized buckling, and project, session and service control. **Nothing in the existing API was removed or renamed.**

## Summary

There are eight capability areas. They are ordered by how much each one changes what a customer can automate.

### 1. Updating and deleting elements — *full CRUD*

In 2027 elements could only be created and read. 2027.1 adds three endpoints:

- `UpdateElement` updates structural elements and loads.
- `UpdateInformationalElement` updates load cases, families, combinations, structural systems, release templates and design templates.
- `DeleteElements` removes several elements in a single call.

An update takes the element id in the query string and the **complete** object in the body. It accepts the same polymorphic set of types as the matching Create endpoint, so changing one property is a read-modify-write round trip.

> **Impact:** this completes the object lifecycle. A model can now be kept in sync with an external source, such as BIM, a spreadsheet or a configurator. Until now it could only be rebuilt from scratch.

### 2. Expert design — *new*

The API can now drive the Expert design modules end to end.

- **Design templates.** Steel × linear design templates are new informational elements. There are three leaves: `EC3SteelLinearDesignTemplate`, `AISCSteelLinearDesignTemplate` and `CSASteelLinearDesignTemplate`. `ElementLinear.designTemplateId` references a template. `AssignDesignTemplateToElements` applies one template to many elements, or detaches them, without touching anything else on the element.
- **Design properties of combinations.** `Combination` gains `designCalculations` and per-family design blocks: `concreteDesign`, `steelDesign`, `timberDesign` and `compositeDesign`.
- **Calculation.** `LaunchDesignCalculation` runs the design engine of one material family (`Concrete`, `Steel`, `Timber` or `Composite`) on the whole model or on a selection. The FEM analysis must have been run first.
- **Results.** `GetDesignResults` returns the design verifications element by element and mesh cell by mesh cell. Today it answers **steel × linear elements × Eurocode 3**. The query is polymorphic so that other families can be added without a contract change.
- **Steel calculation settings.** The EC3 and AISC / CAN-CSA calculation settings are readable and writable through the new model-settings endpoints (see area 3).

> `LaunchDesignCalculation`, `GetDesignResults` and `AssignDesignTemplateToElements` are compiled behind a server build switch, which is **on** in this build. See [docs/HELP.md](docs/HELP.md).

> **Impact:** a script can go from geometry to verified work ratios without opening the interface.

### 3. Automatic combinations and model settings — *new*

- `GenerateCombinations` runs the same generation as the Combinations dialog of the desktop application. It reads the coefficients from the load cases and the generator options from the model. Generation is additive, so existing combinations are kept.
- `GetModelSettings`, `SetModelSettings` and `ResetModelSettings` read, write and reset one group of model-wide settings. A group is named by `eModelSettingsCategory`, and its shape is selected by `$type`. There are three groups today:
  - combination generation, with 5 shapes: Eurocode, Eurocode 2nd generation, US, Canada and Greenhouse;
  - steel EC3 calculation;
  - steel AISC / CAN-CSA calculation.
- The load case coefficients gain the EN 1990 2nd generation partial factors:
  - `LoadCaseCombinationsCoefficients`: `coeff2ndGenGamma*`;
  - `LoadCaseDeadLoadsCoefficients`: `isWater`, `reductionFactor` and the favourable / stabilising `coeff2ndGen*` factors.

> **Impact:** a model built through the API reaches a complete, code-conforming set of combinations in one call, instead of the caller writing every combination by hand.

### 4. User-defined cross-sections — *new*

`CreateUserSection` creates a section whose characteristics are supplied by the caller, in SI units. These are the area, the moments of inertia, the torsional and warping constants, the elastic and plastic moduli and the shear areas. The outline can optionally be described as well, with polygons and circles that add or remove material, so built-up shapes and holes can be expressed. The application's section catalog is not touched: the section lives in the model. A name that already exists is updated rather than duplicated, and its existing id is returned.

> **Impact:** profiles the catalog does not carry become usable, such as built-up sections, customer-specific profiles and sections computed in other software.

### 5. Structural systems and edge releases — *new*

**Systems** become API objects through `StructuralSystem`. A system has a parent, behaviour coefficients, imposed directions, top and bottom levels, a level number, a colour, a wall-group flag and sub-system ids. Every structural element gains `systemIDs`:

- **On create**, the element goes into the first listed system and is added to the rest. With the field empty, it lands in the model's default root system.
- **On update**, the listed systems replace the element's membership entirely.

**Linear release templates** (`LinearReleaseTemplate`) are named, per-degree-of-freedom descriptions of how the edge of a planar element connects to the rest of the structure. They live in a model-level pool. `ElementPlanar` gains `linearReleases`, with one entry per edge in edge order, and `selectedReleaseName` for the case where every edge shares one template.

> **Impact:** generated models carry levels, groups and realistic edge conditions, so they can be navigated, reviewed and handed over like a hand-built model.

### 6. Reference geometry: points and poly lines — *new*

`ElementPoint` and `ElementPolyLine` are reference objects with no stiffness and no load. They drive the mesh, other elements snap to them, and under Eurocode a point can serve as the pivot of the steel imperfection forces. They use the generic element endpoints for create, read, update, query and delete. `ElementLinear.sectionOrientationPointId` orients a member's cross-section towards a point instead of by a fixed angle.

### 7. Generalized buckling analysis — *new*

A new load case family and load case type carry the buckling parameters: number of modes, maximum lambda, tolerance and iteration limit. A new result type (`generalizedBucklingRes`, `ResGeneralizedBuckling`) returns the critical load multiplier per mode. The mode index travels alongside the load case, so these results are read through the new `GetResultsByQuery` endpoint. That endpoint takes the whole query as one polymorphic payload.

> **Impact:** stability studies can be set up, run and read entirely from a script.

### 8. Project, session and service control — *new*

- **Saving and closing.** `SaveProject` and `SaveProjectAs` save the project. `CloseProjectWithoutSave` and `CloseSessionWithoutSave` close it and discard changes. `CloseProject` and `CloseSession` are now documented as *save, then close*.
- **Environment.** `Environments.designCodes` lets `NewProject` and `OpenProject` impose the design standards and national annexes of the session, overriding what the localization resolves to. `GetEnvironment` reads back what the session actually holds.
- **Model state.** `GetAnalysisModelStatus` reports where the model stands in the *mesh → FEM → design* chain. It is a cheap read, so it can be called at any time.
- **Service.** The new `Service` tag has two endpoints. `GetVersion` doubles as a liveness probe. `GetStatus` reports whether the service can run model operations, and if not, why: licence, start-up or shutdown.

> **Impact:** unattended and server-side runs can be controlled and diagnosed properly. A script can check health before it starts, save where it chooses, and abandon a run cleanly.

## New endpoints

There are 20 new endpoints, taking the total from 22 to 42. None were removed or renamed. `GetVersion` and `GetStatus` sit under the new `Service` tag. All the others are under `Model`.

### Editing the model

| Endpoint | What it does | Request | Response |
|---|---|---|---|
| `POST /api/Model/elements/UpdateElement` | **Updates an existing element.** The id goes in the query string, and the complete object with its new properties goes in the body. Accepts the same polymorphic variants as `CreateElement`. | `ElementBase` (oneOf) + `elementId` | `BooleanApiResponse` |
| `POST /api/Model/elements/UpdateInformationalElement` | **Updates a non-geometric element:** a load case, family, combination, structural system, release template or design template. | `InformationalElementBase` (oneOf) + `elementId` | `BooleanApiResponse` |
| `POST /api/Model/elements/DeleteElements` | **Deletes several elements in a single call.** Supported today: structural elements (linear, planar, supports, single piles, mass), loads, and points and poly lines. | `int64[]` (EIDs) | `BooleanApiResponse` |
| `POST /api/Model/sections/CreateUserSection` | **Creates a user-defined section.** The body must carry `"$type": "UserSection"`. Values are in SI units. An existing name means update, not duplicate. | `UserSection` | `EIDApiResponse` |

| Endpoint | What it does | Request | Response |
|---|---|---|---|
| `POST /api/Model/analysis/GetResultsByQuery` | **Results query as a single payload.** The result type, the target ids and the load case travel together as one polymorphic object, so a load case can carry more than its id. | `POST /api/Model/analysis/GetDesignResults` | **Reads the design verifications** of the listed elements, per mesh cell, with the governing combination. Today it answers steel × linear × Eurocode 3. | `ResultsQueryDesign` (oneOf; today `ResultsQueryDesignSteelLinear`) | `ResBaseListApiResponse` |

## Changed endpoints

Seven of the 22 existing endpoints changed. Every change is additive or a clarification of the documentation.

| Endpoint | Change |
|---|---|
| `POST /api/Model/elements/CreateElement` | The accepted body variants grow from **25 to 27** with `ElementPoint` and `ElementPolyLine`. No variant was removed. |
| `POST /api/Model/elements/CreateInformationalElement` | The accepted body variants grow from **42 to 53**: `StructuralSystem`, `LinearReleaseTemplate`, `LoadCaseFamily_AnalysisBuckling`, `LoadCase_Buckling`, and the design template hierarchy (`DesignTemplate`, `LinearDesignTemplate`, `SteelLinearDesignTemplate`, `EC3…`, `NorthAmerican…`, `AISC…`, `CSASteelLinearDesignTemplate`). No variant was removed. |
| `POST /api/Model/analysis/GetResults` | `eResType` accepts a new value: **5 — `generalizedBucklingRes`**. The summary now states that this endpoint serves a single load case or combination identified by its id. Anything that needs more goes through `GetResultsByQuery`. |
| `POST /api/Model/management/NewProject` | The `Environments` body gains the optional `designCodes`. A relative `filename` is now documented as resolved against the server's working directory (the `/w` start-up option, otherwise the folder the server was started from). The target folder must already exist. |
| `POST /api/Model/management/OpenProject` | Same as `NewProject`: optional `designCodes`, and the same relative-path resolution. |
| `POST /api/Model/management/CloseProject` | Now documented: **saves the open project, then closes it**. Use `CloseProjectWithoutSave` to discard changes. |
| `POST /api/Model/management/CloseSession` | Now documented in detail. The call returns at once, and the shutdown follows in the background about 5 seconds later. The server waits for a running operation, **saves and closes the open project** (no `CloseProject` is needed first), releases the licence and exits. From the call on, every other `api/Model` request gets **HTTP 503 `SERVICE_STOPPING`**, and `GetStatus` answers `Stopping`. Calling it again is harmless. |

## Compatibility

This section covers what to know before running a 2027 client against a 2027.1 server.

> **Overall verdict: forward compatible.** Zero endpoints deleted, zero schemas deleted, zero fields removed, zero renames. An existing integration has nothing to rewrite. The points below are things to **verify**, not things to rewrite.

> **The versions can now be told apart.** `info.version` is `1.27.1`, where 2027 was `1.27.0`. At run time, `GET /api/Service/GetVersion` answers the same question.

### 1. Stricter validation of planar contours — *behaviour change*

Every object built on a planar contour has its `geomPtsList` validated with the same rule as the interactive model. This covers planar elements, planar supports, load areas and surface loads. The contour needs:

- at least 3 points;
- no coincident points;
- no three consecutive collinear points;
- all points in one plane;
- no self-intersection.

On create the element is not created. On update nothing is modified. Generated geometry that slipped through in 2027 can therefore be refused in 2027.1. This change can break a workflow that worked in 2027, so check it against existing scripts first.

### 2. `ElementRigidPunctualSupport.constraintsType` — *behaviour change*

In 2027 a rigid punctual support carried only `restraints`. In 2027.1 it also has `constraintsType`, which is required in the schema and defaults to `fix`, as on rigid linear and planar supports. The restraint type is `fix`, `SupportHinge` or `other`, and the custom per-DOF `restraints` apply with `other`.

A 2027 script that defines a hinge or custom restraints through `restraints` alone gets the default `fix`. It must now also send `constraintsType`: `SupportHinge` for a pinned support, `other` for custom restraints. The 2027.1 samples were updated this way. For example, `WindSnow3DBuildingAutoGeneration.cs` now sets `ConstraintsType = SupportHinge` next to the same `Restraints` it used in 2027.

### 3. `Section.$type` became mandatory

`Section` lists `$type` in `required`, alongside `name` and `type`. Code generators and contract validators built on the 2027.1 schema will treat a section body without `$type` as invalid, so always send it. `CreateUserSection` refuses a body that is not `"$type": "UserSection"`.

### 4. `footingEnable` became mandatory

This applies to `FootingDimensions` and `FootingDimensionsLinear`. Send the field explicitly in every footing body.

### 5. Extended enumerations and response types

`ResultType`, `ElementTypeEnum`, `InformationalElementTypeEnum`, `eLoadCaseType` and eight climatic enumerations gained values. Four response envelopes can carry polymorphic types an old client does not know. A .NET client with a strict string-enum converter, or a client generated from the 2027 schema, will throw on deserialization when it reads a model that uses any of the new features. **Regenerate the client from the 2027.1 schema.**

### 6. Session close is asynchronous

`CloseSession` returns before the server has finished. The project is saved, the licence is released and the process exits in the background. A script that closes a session and immediately starts another against the same host should wait until `GET /api/Service/GetStatus` no longer answers `Stopping`. In the meantime, `api/Model` calls receive HTTP 503 `SERVICE_STOPPING`.

### 7. Design standards in the environment

`Environments.designCodes` is optional. Left null, the session behaves as in 2027. When it is set, a standard and annex combination the desktop application could not produce fails the **whole** `NewProject` / `OpenProject` call, and the reason is in the diagnostics.

## Testing guide

These coverage areas are derived from the schema delta and ordered by risk.

### Update elements — *Priority 1 · new functionality*

- Update every polymorphic subtype `UpdateElement` accepts, not just beams and slabs.
- Send a non-existent `elementId`, an id whose real type differs from the body sent, and a body without `$type`.
- The body is the complete object. Check that a read-modify-write round trip preserves every field you did not change.
- Make a geometry change that invalidates something downstream, such as a mesh already generated or results already computed. Check `GetAnalysisModelStatus` afterwards.
- Change the section of a variable-inertia beam so that start and end fall into different families. The change must be rejected and the element must stay unchanged.
- Update an element with an invalid planar contour. Nothing may be modified.

### Delete elements — *Priority 1 · new functionality*

- Send an empty list (`ELEMENT_DELETE_EMPTY_INPUT`), duplicate ids, and non-existent ids mixed among valid ones. The response is a single boolean, so pin down whether the call is atomic.
- Delete an unsupported type. It must return a clear error, not a silent success.
- Delete an element referenced by another: a section in use, a system with children, a release template applied to edges, a point used as an orientation target.
- Delete a support or a load and re-run the analysis. Stale results must not survive.
- Delete large batches, for performance and for partial-failure behaviour.

### Expert design — *Priority 1 · new functionality*

- `LaunchDesignCalculation` before `LaunchAnalysis` must be refused with an explicit diagnostic.
- Check that at least one combination lists the design calculation in `designCalculations`. Otherwise the engine has nothing to verify.
- Design templates: create, update and assign each leaf (EC3, AISC, CSA) on a model configured for the matching code. Assigning to an element of the wrong kind, material or code is reported per element and leaves it untouched.
- Detach a template with `designTemplateId = 0`. The element keeps its current expert values.
- `GetDesignResults` with an empty id list (refused), with a non-Eurocode steel code (refused by name), and before the design was run (refused).
- Compare the results with the Advance Design reports for the same model. Units are SI in the API, while the reports print kN, kN·m and cm.

### Combinations and model settings — *Priority 1*

- Run `GenerateCombinations` on a model built entirely through the API. Check the number and content of the combinations against the desktop dialog on the same model.
- Generation is additive. Run it twice and check the result. Check `limitExceeded` when the configured maximum is reached.
- Do a get → set → get round trip for each `eModelSettingsCategory`, and run `ResetModelSettings` afterwards.
- Send a settings shape that does not match the model's combination standard.
- Use the 2nd generation load case coefficients on a model that is not configured for EN 1990 2nd generation.

### User-defined sections — *Priority 1 · numerical validation*

- Test the documented constraints: A > 0, Iy > 0, Iz > 0, It > 0, **Iy·Iz − Iyz² > 0**, Avy and Avz ≤ A, Wpl ≥ Wel.
- A negative Iyz must be accepted, because it is a signed quantity.
- A duplicate name updates rather than creates. Check that the returned id is the existing one and that elements using the section pick up the new characteristics.
- `"$type": "Section"` sent to `CreateUserSection` must fail.
- An omitted outline gives the default 50 × 50 mm square. Test contours with holes and with circles, and an invalid contour.
- Assign a user section and run an analysis. Stiffness and self-weight must reflect the supplied values.

### Project, session and service — *Priority 1*

- `SaveProjectAs` with a relative path, an absolute path, a missing folder, a doubled extension and an over-long path.
- `CloseProject` saves while `CloseProjectWithoutSave` discards. Reopen the project and check which one ran.
- `CloseSession` followed immediately by an `api/Model` call must return 503 `SERVICE_STOPPING`. `GetStatus` must answer `Stopping` until the process exits.
- `GetStatus` while starting, with no licence, and with a licence that does not cover a design family.
- `NewProject` with `designCodes` overrides, and `GetEnvironment` afterwards. Test an invalid standard and annex combination.

### Structural systems and edge releases — *Priority 2*

- Empty `systemIDs` on create puts the element in the root system. A non-existent id must make the create fail.
- An update that changes membership is a full replacement. Check that the element leaves the systems it is no longer listed in.
- Nested systems, and round-tripping the level properties.
- Send `linearReleases` with a different number of entries than the element has edges. Check the edge ↔ point ordering.
- Omit releases on create. The built-in fixed template must be applied to every edge.

### Buckling and the query endpoint — *Priority 2 · new serialization mechanism*

- `$type` missing, unknown, or inconsistent with the payload.
- Ask for a mode that does not exist or is above the number of computed modes.
- Parity with `GetResults`: the same FEM query through both endpoints must return identical results.
- The buckling result is model-wide, not per element.

### Regression against 2027 — *Priority 1 · non-regression*

- Run the full 2027 test suite unchanged against 2027.1. That covers all 22 existing endpoints.
- Find planar contours tolerated in 2027 and quantify how many existing scripts fall foul of the new validation.
- Test rigid punctual supports created with custom `restraints` and no `constraintsType`.
- Test `Section` bodies without `$type` and `FootingDimensions` bodies without `footingEnable`.
- Make a client generated from the 2027 schema read responses that carry the new types and enum values.

### End-to-end round trips — *Priority 2 · integration*

- Build a model through the API, read it back and compare it field by field. Include `userName`, `systemIDs`, the release fields and `designTemplateId`.
- Create → update → delete the same element, and check model consistency after each step.
- Run a full chain: `NewProject` → elements → `GenerateCombinations` → `LaunchAnalysis` → `LaunchDesignCalculation` → `GetDesignResults` → `SaveProjectAs`. Then open the project in the interface.
