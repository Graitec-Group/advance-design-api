# 2027.1 API Capabilities

*Advance Design · API · 2027 → 2027.1*

## From model generator to engineering workflow

With 2027.1 the API does more than **build and analyse** a model. It can also **maintain** the model, **design** it and **manage the session** around it. In 2027 a script could create a model and read its finite-element results. In 2027.1 it can:

- correct and delete what it created;
- generate the load combinations;
- run the Expert design;
- organise the model into systems and levels;
- save and close the project on its own terms.

| New capability areas | New operations | Removals or renames | Behaviour changes to watch |
|:---:|:---:|:---:|:---:|
| **8** | **20** | **0** | **2** |

## The eight capabilities

They are ordered by how much they change what a customer can automate.

### 1. Updating and deleting elements — *new*

| Before | Now |
|---|---|
| Elements could only be created and read. A wrong property meant rebuilding the model from scratch, and nothing could be removed. | Any element can be updated in place: geometry, section, material, supports, loads and masses. So can the non-geometric objects: load cases, families, combinations, systems and templates. Several elements can be deleted in one call. |

Update covers the same range of types the API can create, so no class of objects has to be handled through the interface. Deletion works in bulk, which matters in practice: reconciling a model against a changed source usually removes many objects at once.

**Unlocks:** keeping a model in step with an external source (BIM, a spreadsheet, a configurator) instead of regenerating it each time. Create, read, update and delete together are the baseline any integrator expects before committing to an API.

### 2. Expert design from a script — *new*

| Before | Now |
|---|---|
| The API stopped at finite-element results. Design checks had to be launched and read in the interface. | A script can assign steel design templates, mark which combinations each design uses, launch the design calculation and read the verification results element by element. |

The design calculation can be launched for concrete, steel, timber and composite. Design templates and detailed results are available today for **steel linear members**: templates for Eurocode 3, AISC and CAN/CSA, and results for Eurocode 3. The contract is built so the other families can be added without changing it.

**Unlocks:** a fully automated chain from geometry to verified work ratios, for parametric studies, optimisation loops and configurators.

### 3. Automatic load combinations and model settings — *new*

| Before | Now |
|---|---|
| Every combination had to be written out by the caller, coefficient by coefficient. | One call generates the combinations exactly as the Combinations dialog does, for the Eurocode (including the 2nd generation), US, Canadian and greenhouse standards. The generator options and the steel calculation settings can be read, written and reset. |

**Unlocks:** code-conforming combination sets without the caller having to know the combination rules. This removes one of the most error-prone parts of an automated model.

### 4. User-defined cross-sections — *new*

| Before | Now |
|---|---|
| Only sections from the catalog or from the parametric shapes. Anything else had to be approximated or added by hand. | The caller supplies the sectional properties directly (area, inertias, torsional and warping constants, section moduli, shear areas) and, if wanted, the outline as well, including built-up shapes and holes. |

The section lives in the model, not in the application's catalog, so nothing global is modified. Re-sending a section under an existing name updates it rather than creating a duplicate, which is the behaviour a repeated sync needs.

**Unlocks:** built-up sections, customer-specific profiles and sections computed in other software. These are the cases that previously blocked full automation.

### 5. Structural systems and edge releases — *new*

| Before | Now |
|---|---|
| Generated models were flat: every element sat in one undifferentiated container, with no levels and no grouping. Slab and wall edges were always fixed. | Systems and building levels are API objects, and every element declares which systems it belongs to. Slab and wall edges can carry named release templates instead of the default fixed connection. |

Systems can be nested, can act as storeys with top and bottom levels and a level number, and can be marked as wall groups. An API-built model therefore carries the same organisation an engineer would give it by hand.

**Unlocks:** generated models that an engineer can actually navigate, review and hand over. That is the difference between a model that is technically correct and one that is usable.

### 6. Reference geometry: points and poly lines — *new*

Points and poly lines are now API objects. They have no stiffness and no load, but they drive the mesh, give other elements something to snap to, and can orient a member's cross-section.

**Unlocks:** finer control of the mesh, and models that keep their construction geometry.

### 7. Generalized buckling analysis — *new*

A buckling analysis can be defined, run and read entirely from a script: the number of modes and the solver parameters, then the critical load multiplier per mode.

**Unlocks:** stability studies as part of an automated workflow.

### 8. Project, session and service control — *new*

| Before | Now |
|---|---|
| A project could be opened and closed, but not saved on demand, saved under another name, or abandoned without saving. The design standards came only from the localization. There was no way to ask the server whether it was ready. | Save and Save As are explicit. Projects and sessions can be closed with or without saving. The design standards and national annexes can be imposed per session and read back. The model reports where it stands (mesh, analysis, design). The service reports its version, licence and readiness. |

**Unlocks:** unattended and server-side runs that can be monitored and diagnosed. A script can check health before it starts, save where it chooses and abandon a run cleanly.

## What this means in practice

**Two-way integration is now possible.** With update and delete in place, an Advance Design model can take part in a BIM workflow continuously, not only as a one-time export target.

**Fewer blockers in automation projects.** Automatic combinations, user sections, system management and Expert design remove the usual reasons why an automation project stalled and fell back to manual work.

**Existing integrations keep working.** Nothing was removed or renamed, so integrations built against 2027 move to 2027.1 without a migration. Regenerating the client from the 2027.1 schema is recommended so it understands the new types.

---

## The two things to watch

### Slab and wall outlines are validated more strictly

Contours of planar elements, planar supports, load areas and surface loads are now checked the way the interactive model checks them. A contour cannot have duplicate points, three consecutive points in a straight line, or a self-intersection. Generated geometry that slipped through in 2027 can be rejected in 2027.1.

### Rigid punctual supports now have an explicit restraint type

A rigid punctual support now has `constraintsType`, which defaults to `fix`, as on rigid linear and planar supports. Scripts that defined a hinge or custom restraints through the degree-of-freedom list alone get a fixed support. They must also send `constraintsType`: `SupportHinge` for a pin, `other` for custom restraints.

Both changes are worth a targeted check against existing scripts.
